# Git 워크플로

이 문서는 **통합 규칙**을 다룬다. 로컬 개발 환경은 [setup.md](setup.md), 병렬 작업 디렉터리 운영은 [worktrees.md](worktrees.md)를 본다.

## 브랜치 이름

- 기능: `feature/짧은-설명` (예: `feature/chess-undo`)
- 수정: `fix/이슈-요약`
- 문서만: `docs/요약` 허용

## 기본 원칙

- 로컬 개발 방식은 각자 선택할 수 있다.
- 하지만 기본 브랜치에 들어가는 변경은 **브랜치 + Pull Request + GitHub Checks** 경로를 따른다.
- 로컬 확인은 권장되지만, 최종 통합 기준은 GitHub의 리뷰와 체크 상태다.
- 형상 관리 텍스트 언어는 로컬/팀 설정을 따른다. 같은 PR 안에서는 이슈, PR 본문, 커밋 메시지의 언어를 가능하면 섞지 않는다.

## 커밋 메시지

- 한 커밋에 한 주제. 첫 줄은 요약(약 50자 이내)을 쓴다.
- 한국어를 쓰는 경우: 변경 내용을 자연스러운 한국어 요약으로 적는다.
- 영어를 쓰는 경우: 명령형 문장을 권장한다.
- 필요 시 본문에 이유·에디터에서 확인할 일을 적는다.

한국어 예:

```
체스 폰 승급 조건 검사 추가

- 인스펙터에 새 필드 추가 시 씬에서 재할당 필요
```

영어 예:

```
Add pawn promotion check in ChessGameManager

- Reassign scene references if new inspector fields are added
```

## Pull request 전 확인 (Unity)

- [ ] 관련 씬·프리팹·인스펙터 참조가 깨지지 않았는지 에디터에서 확인
- [ ] Play 모드에서 요청한 동작이 재현되는지
- [ ] 공개 API나 인스펙터 필드가 바뀌었다면 인접 문서 또는 `docs/` 갱신
- [ ] 관련 이슈나 엄브렐라 이슈가 있으면 PR 본문에서 연결

## Pull request 운영

- 큰 작업은 엄브렐라 이슈 아래에서 작은 PR로 나눈다.
- PR 하나는 한 주제를 다루고, 리뷰 가능한 크기를 유지한다.
- 문서·정책 PR과 코드·CI PR을 섞어 키우지 않는다.
- 플랫폼별 빌드처럼 무거운 변경은 빠른 검증 PR과 분리한다.
- 이슈와 PR 본문 언어는 로컬/팀 설정을 따른다. 이 프로젝트의 현재 로컬 선호 예시는 한국어다.

## 머지 방식과 로컬 정리

- 기본 선호는 squash merge다. 작은 PR 단위 지속 통합에서는 `main` 히스토리를 PR 단위로 읽기 쉽게 유지할 수 있다.
- squash merge 후에는 로컬 feature 브랜치의 커밋 SHA가 `main`에 그대로 포함되지 않으므로 `git branch -d`가 실패할 수 있다.
- 이 경우 `git diff --stat main..feature/<name>`가 비어 있는지 확인한 뒤 `git branch -D feature/<name>`로 정리한다.
- 일반 merge commit을 사용한 경우에는 feature 브랜치 커밋이 `main`에 포함되므로 보통 `git branch -d feature/<name>`로 정리된다.
- 커밋 단위 히스토리를 보존해야 하는 큰 작업은 squash 대신 일반 merge를 선택할 수 있다.
- 원격 브랜치를 GitHub에서 삭제했다면 로컬에서는 `git fetch --prune origin`으로 원격 추적 브랜치를 정리한다.

## 셀프리뷰 코멘트

- 비자명한 라인 변경은 가능하면 PR에 셀프리뷰 라인 코멘트를 남긴다.
- 특히 버전, 경로, CI 조건, 빌드 타깃, 에이전트 규칙처럼 다음 사람이 실수로 되돌리기 쉬운 변경은 근거를 같이 남긴다.
- 변경 근거가 앞으로도 계속 필요하면 PR 코멘트만 남기지 말고 코드 주석이나 문서 본문에도 반영한다.
- 셸 스크립트, CI 스크립트, 정규식, 경로 계산처럼 읽는 난도가 높은 변경은 주석을 더 적극적으로 남긴다.
- 단순 오탈자, 명백한 문장 다듬기, 주변 맥락으로 충분히 설명되는 변경에는 코멘트를 남기지 않아도 된다.

## 스크립트 작성 기준

- 스크립트는 짧더라도 실패 조건과 의도를 블록 단위 주석으로 남긴다.
- CI에서만 실패하는 검증은 "무엇을 막으려는지"를 주석이나 PR 셀프리뷰 코멘트로 설명한다.
- `bash`/`sh` 스크립트는 PowerShell이나 C#보다 낯선 사람이 많으므로, 경로 계산·문자열 치환·정규식 주변은 특히 설명한다.
- 단순 명령 나열보다 유지보수자가 안전하게 고칠 수 있는 구조를 우선한다.

## GitHub-first 통합 정책

- 실험과 프로토타이핑은 로컬 중심이어도 된다.
- 공유 브랜치 통합은 GitHub 기준으로 관리한다.
- 보호 브랜치에는 직접 푸시하지 않는다.
- 병합 가능 여부는 개인 PC 상태가 아니라 저장소의 체크 통과 기준으로 판단한다.

## 빠른 PR 체크

- Pull Request에는 최소한의 빠른 검증 워크플로를 붙인다.
- 이 빠른 체크는 Unity 전체 빌드 전 단계에서 문서 드리프트, 기본 구조 누락, 핵심 설정 이상을 먼저 잡는 역할을 한다.
- 무거운 플랫폼 빌드나 Unity 테스트는 별도 워크플로로 분리한다.
- GitHub Actions는 public 저장소의 standard GitHub-hosted runner 사용이 무료지만, larger runner와 artifact/cache/storage는 과금 또는 플랜 한도 영향을 받을 수 있다.
- CI 워크플로의 runner 종류, 캐시, 아티팩트 업로드, 보관 기간을 바꿀 때는 비용 리스크를 주요 리뷰 포인트로 확인한다.

## 첫 커밋에 포함할 것

- **포함 권장**: `Assets/`(스크립트, 씬, 프리팹 등), `ProjectSettings/`, `Packages/`, 루트 `AGENTS.md`, `docs/`, `.cursor/rules/`, `.gitignore`
- **제외됨**: `.gitignore`에 따라 `Library/`, `Temp/`, `Logs/`, `UserSettings/` 등은 커밋하지 않음

처음 `git add` 후 `git status`로 불필요한 대용량·로컬 폴더가 올라가지 않았는지 본다.
