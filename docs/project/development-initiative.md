# 개발 이니셔티브 방향

이 문서는 현재 프로젝트의 개발 운영 방향과 플랫폼 우선순위를 고정한다. 세부 구현 이슈가 흔들릴 때는 이 문서를 먼저 기준으로 본다.

## 결론

- 개발 주력은 **로컬 Unity 에디터와 로컬 에이전트 작업**이다.
- PR과 CI/CD는 무거운 자동화가 아니라, 변경을 작게 통합하고 실수를 줄이는 **얇은 안전망**으로 둔다.
- 초기 플레이 대상 플랫폼은 **PC**로 고정한다.
- PC Delivery의 1차 형태는 Windows artifact 또는 GitHub Release asset이다.
- WebGL은 무료 공유 링크 후보로 유지하되, 초기 플랫폼 결정의 중심축은 아니다.
- Android, iOS, TestFlight, Google Play, App Tester 같은 모바일 배포는 크로스플랫폼 지원 결정 전까지 보류한다.

## 왜 로컬 중심인가

Unity 프로젝트는 백엔드 서비스처럼 CI가 통과하면 동작 품질이 충분히 보장되는 구조가 아니다. 씬, 프리팹, 인스펙터 참조, TMP 렌더링, 입력감, 화면 비율, 전투 흐름은 로컬 에디터와 실제 플레이 확인이 계속 필요하다.

따라서 이 프로젝트에서 CI/CD의 역할은 다음으로 제한한다.

- 저장소 구조, 문서 링크, Unity 버전, Build Settings 같은 기본 드리프트를 빠르게 잡는다.
- EditMode/PlayMode 테스트처럼 자동화 가능한 규칙 회귀를 잡는다.
- 수동 실행 workflow로 PC 빌드 artifact를 만들고 smoke test 기록을 남긴다.
- main에 들어간 변경이 다음 작업자와 다음 에이전트에게 추적 가능하도록 한다.

반대로 다음을 CI/CD에 과도하게 기대하지 않는다.

- 모든 PR마다 무거운 플랫폼 빌드를 required check로 강제하지 않는다.
- 에디터에서만 확인 가능한 시각/입력/프리팹 품질을 CI 통과로 대체하지 않는다.
- 모바일 스토어 배포처럼 계정, 서명, 비용, 운영 정책이 얽힌 경로를 초기 완료조건으로 삼지 않는다.

## PR의 역할

PR은 백엔드식 배포 게이트라기보다, Unity/에이전트 개발에서 다음 정보를 남기는 통합 단위다.

- 어떤 이슈를 닫는지
- 어떤 씬, 설정, 스크립트, 문서가 바뀌었는지
- 로컬 에디터에서 무엇을 확인했는지
- CI로 무엇을 확인했는지
- 비자명한 설정 변경의 근거가 무엇인지

작은 PR은 유지한다. 다만 로컬에서 빠르게 실험한 뒤, main 반영 직전에 PR로 맥락과 검증을 정리하는 흐름을 우선한다.

## 플랫폼 우선순위

| 우선순위 | 플랫폼/경로 | 현재 방침 |
| --- | --- | --- |
| 1 | PC/Windows artifact | 초기 버전의 주 Delivery 경로 |
| 2 | GitHub Release asset | 수동 release tag 기준 장기 보관 후보 |
| 3 | WebGL/GitHub Pages | 무료 공유 링크 후보. PC 우선 흐름을 보조 |
| 보류 | Android/iOS/TestFlight/Play Console | 크로스플랫폼 지원 결정 전까지 진행하지 않음 |

## 현재 스프린트 완료조건

- 로컬 Unity에서 PC 기준 플레이 흐름을 확인할 수 있다.
- main 기준 컴파일 오류가 없다.
- PR 빠른 체크는 계속 required 후보로 유지한다.
- Windows PC 빌드 artifact를 수동 workflow로 생성할 수 있다.
- 최신 PC 빌드 다운로드 방법이 문서화되어 있다.
- 모바일 배포는 명시적으로 보류 상태로 기록되어 있다.
