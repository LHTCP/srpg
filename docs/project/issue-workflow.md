# 이슈 트리 작업 방식

이 문서는 GitHub 이슈를 엄브렐라, 리서치, 의사결정, 구현 단위로 나누어 운영하는 기준을 다룬다. Git 브랜치와 PR 운영은 [workflow.md](workflow.md), GitHub 브랜치 보호와 required checks는 [github-governance.md](github-governance.md)를 본다.

## 기본 원칙

- 큰 목표는 엄브렐라 이슈로 추적하고, 실제 변경은 작은 최말단 이슈와 PR로 나눈다.
- 리서치와 의사결정은 구현 이슈에 섞지 않고 별도 이슈로 만든다.
- 구현 이슈는 가능하면 PR 하나로 닫을 수 있는 크기로 유지한다.
- 이슈 관계는 GitHub Relationships와 이슈 본문 링크를 함께 사용한다.
- 이슈 타입과 라벨은 검색, 필터, 자동화의 힌트다. 이슈 본문을 대체하지 않는다.

## 이슈 타입과 라벨 기준

GitHub 공식 Issue Type을 쓰는 경우 다음 기준을 따른다. 공식 Issue Type을 쓰지 않는 저장소나 시점에서는 같은 의미의 `type:` 라벨을 사용한다.

| 구분 | 사용 기준 |
| ---- | ---- |
| Feature | 사용자 또는 운영자가 체감하는 기능, 배포 경로, 큰 개선 목표 |
| Task | PR 하나로 닫을 수 있는 문서, 설정, CI, 코드 작업 |
| Bug | 기대 동작과 실제 동작이 다른 문제를 수정하는 작업 |

보조 라벨은 다음처럼 쓴다.

| 라벨 | 사용 기준 |
| ---- | ---- |
| `type: umbrella` | 여러 하위 이슈를 묶는 추적용 이슈 |
| `type: research` | 선택지, 제약, 공식 문서, 비용, 계정 요구사항을 조사하는 이슈 |
| `type: decision` | 리서치 결과를 바탕으로 방향을 확정하는 이슈 |
| `type: task` | PR 하나로 닫을 수 있는 구현 또는 문서 작업 |
| `type: bug` | 재현 가능한 오류 수정 작업 |
| `area: cicd` | CI, 테스트, 빌드 자동화 |
| `area: release` | 배포, 릴리스, 아티팩트, 플레이 링크 |
| `area: workflow` | 이슈, PR, 브랜치, 운영 규칙 |

## Parent-Child 설정 기준

GitHub Sub-issues의 Parent-Child 관계는 작업 분해와 진행률 추적에 사용한다.

- 엄브렐라 이슈는 여러 Phase 또는 하위 목표의 Parent가 된다.
- Phase 이슈가 필요할 만큼 큰 경우, Phase 이슈를 Parent로 두고 최말단 이슈를 Child로 둔다.
- 최말단 이슈는 일반적으로 Child를 더 만들지 않는다.
- 같은 PR로 닫을 작업끼리는 억지로 여러 Child로 쪼개지 않는다.
- 서로 다른 책임 파일, 플랫폼, 계정 설정, 검증 경로를 가진 작업은 별도 Child로 나눈다.

Parent 이슈 본문에는 하위 이슈 체크리스트를 함께 둔다. GitHub 관계가 UI에서 보이더라도, 본문 체크리스트는 맥락과 완료조건을 빠르게 읽기 위한 보조 색인으로 유지한다.

## Blocks 관계 기준

작업 순서가 중요한 경우 GitHub Relationships의 `blocked by` 또는 `blocking` 관계를 설정한다. 동시에 이슈 본문에도 `Blocked by` 항목을 남긴다.

본문에도 남기는 이유는 다음과 같다.

- GitHub UI 밖에서 이슈 본문만 읽어도 의존성을 이해할 수 있다.
- 에이전트나 외부 도구가 Relationships API를 완전히 지원하지 않아도 차단 관계를 놓치지 않는다.
- PR 본문이나 릴리스 노트에서 의존성을 복사해 전달하기 쉽다.

차단 관계를 남길 때는 다음 기준을 따른다.

- 선행 이슈가 끝나야 착수 가능한 경우에만 Blocks 관계를 건다.
- 단순 참고, 관련 있음, 같은 Phase라는 이유만으로 Blocks를 걸지 않는다.
- 선행 작업이 선택지 확정이라면 `type: decision` 이슈를 Blocker로 둔다.
- 선행 작업이 실제 동작 검증이라면 해당 `type: task` 또는 `type: bug` 이슈를 Blocker로 둔다.

본문 표기 예:

```md
## 의존성

Blocked by:
- #12 main 컴파일 오류 정리
- #18 CI에서 LFS를 받을지, LFS-free 구조로 갈지 결정
```

## 최말단 이슈 크기 기준

최말단 이슈는 PR 하나로 닫을 수 있어야 한다. PR 본문에는 `Closes #이슈번호`를 넣어 병합 시 자동으로 닫히게 한다.

좋은 최말단 이슈의 기준:

- 책임 파일 또는 책임 영역이 명확하다.
- 완료조건을 3~5개 체크박스로 설명할 수 있다.
- 리뷰어가 한 번에 맥락을 이해할 수 있다.
- 검증 방법이 명확하다.
- 실패해도 되돌리거나 후속 이슈로 분리하기 쉽다.

너무 큰 이슈의 신호:

- 문서, CI, 런타임 코드, 배포 설정이 한 이슈에 섞인다.
- 플랫폼이 WebGL, Windows, Android, iOS처럼 여러 개로 벌어진다.
- 리서치 결론이 나기 전인데 구현까지 포함한다.
- 완료조건을 쓰면 6개 이상으로 길어진다.
- PR 하나가 여러 독립 위험을 동시에 품는다.

이 경우 리서치, 의사결정, 구현 이슈로 다시 나눈다.

## PR 연결 기준

- 구현 이슈는 PR 본문에 `Closes #이슈번호`를 넣는다.
- 리서치나 의사결정 이슈는 결론 문서화 PR로 닫거나, 이슈 댓글에 결론과 후속 이슈를 남기고 닫는다.
- 엄브렐라 이슈는 하위 이슈가 모두 닫히고 최종 완료조건이 충족될 때 닫는다.
- PR 하나가 여러 이슈를 닫을 수는 있지만, 그 경우 같은 책임 영역의 작은 이슈인지 먼저 확인한다.

## 이슈 작성 체크리스트

- [ ] 이슈 타입 또는 `type:` 라벨을 붙였다.
- [ ] 필요한 `area:` 라벨을 붙였다.
- [ ] Parent가 필요한 경우 GitHub Sub-issues 관계를 설정했다.
- [ ] 순서 의존성이 있으면 GitHub Relationships와 본문 `Blocked by`를 함께 남겼다.
- [ ] 최말단 구현 이슈라면 PR 하나로 닫을 수 있는 크기인지 확인했다.
- [ ] 완료조건과 검증 방법을 본문에 적었다.
